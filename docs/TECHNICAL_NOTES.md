# 实现笔记

> 这份文档记录**设计取舍**和**实测数据**，面向想看内部实现的人。
> 安装/用法请看主 [README](../README.md)。

## 1. 总体取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 引擎 | faster-whisper 而不是 openai-whisper | CTranslate2 的 int8 量化在 CPU 上快数倍 |
| 输出 | Markdown 段落而不是 SRT | 目标是"能读的笔记"，不是"贴回视频的字幕" |
| 流水线 vs 单体 | 五层分离，每层可单独跑 | 出问题能定位到哪一层，也方便替换其中一层 |
| CLI vs GUI | 核心逻辑在 CLI，GUI 只是壳 | GUI 通过子进程调 CLI，所以 GUI 崩了核心照样能用 |
| 大模型总结 | **不做** | 引入 LLM 就引入 API key、费用、数据出本机三个问题；转写本身已经够用 |

## 2. 五层流水线的关键参数

| 层 | 命令 / 实现 | 关键参数与理由 |
|---|---|---|
| 1 代理 | 纯 socket 探测 | 优先级：CLI > 硬编码 > 环境变量 > 默认 7890；探测失败自动退化直连并警告 |
| 2 下载 | `yt-dlp` | 优先 `bestaudio`；无独立音轨时选最低画质合并流，最后回退 `best`；`noprogress`（用自己的进度回调）；`proxy` 显式传入 |
| 3 提取 | `ffmpeg` | `-vn -ac 1 -ar 16000 -c:a pcm_s16le` |
| 4 转写 | `faster-whisper` | 见下面第 3~5 节 |
| 5 输出 | 纯 Python | 相邻字幕按语义合并成约 180 字段落 |

**ffmpeg 参数逐个说明：**

| 参数 | 作用 | 不写的后果 |
|---|---|---|
| `-vn` | 不解码视频流 | ffmpeg 会把 1080p 视频也解一遍，实测多花约 1 秒 |
| `-ac 1` | 单声道 | 数据量翻倍，而 Whisper 只用一个声道 |
| `-ar 16000` | 16 kHz | Whisper 内部固定 16 kHz，不转它自己重采样，白费算力 |
| `-c:a pcm_s16le` | 16-bit 小端 PCM | 用压缩格式会引入损耗，且解码又多一步 |

选 PCM 还有个隐性好处：可以用标准库 `wave` + numpy 直接读成数组喂给模型，**完全绕开 PyAV**。
（PyAV 19 删掉了 `metadata_errors` 参数，而 faster-whisper 1.2.1 仍在传，会 `TypeError`。）

## 3. 中英混排：为什么以前会丢段

### 现象

一支中文旁白 + 英文访谈交替的视频，英文段会**整段消失**，或者变成复读幻觉：

```
86.0-88.0  中文字幕。
88.0-90.0  中文文字。
90.0-92.0  中文語字幕.
92.0-94.0  中文中文。
```

### 根因

整段一次性调用 `model.transcribe()` 时，模型会**延续上一段的语言上下文**。中文条件下遇到连续英文，有两种下场：

1. 把英文"翻译"成中文 → 内容失真
2. **直接跳过不输出** → 大段空白

### 对照实验

同一段 150 秒「中文 60s + 英文 45s + 中文 45s」素材：

| 做法 | 字幕条数 | 英文词 | 幻觉 | 覆盖 | 耗时 |
|---|---|---|---|---|---|
| 整段一次性 | 72 | **1** | **13** | 143s/150s | 23.7s |
| 逐块 120s | 20 | 16 | 0 | 107s | 23.4s |
| **逐块 60s** | 26 | **116** | **0** | 117s | 28.9s |
| 逐块 45s | 22 | 21 | 0 | 113s | 34.5s |
| 逐块 30s | 37 | 80 | 0 | 130s | 45.4s |

**60 秒是最优区间**：块再大，一块里语言混杂得更厉害；块再小，边界变多、上下文变碎。

### 最终做法

`CHUNK_SEC = 60`，每块内部：

1. `model.detect_language(audio=chunk)` 单独检测
2. 按检出的语言挑 `initial_prompt`
3. 用该语言 token 转写
4. 时间戳加上块偏移

代价：比整段一次性慢约 25%。**这个交换很值** —— 快 25% 但内容错 90%，没有意义。

### 真实案例

一支 6 分钟的中英混排视频（中文旁白 + Terence Tao 英文访谈）对比如下：

| | Buzz（22k★ 桌面工具） | 本项目 |
|---|---|---|
| 缺失区间 | 38–209s、226–329s（**274s / 363s = 75%**） | 44s / 363s = 12% |
| 英文词 | 4 | **663** |

Buzz 只做了**整段一次**语言检测，所以在英文段上必然失败。详见 [COMPARISON_buzz.md](COMPARISON_buzz.md)。

## 4. 中文简体与标点

### 现象

Whisper 对中文默认输出**繁体**，而且经常**整段不加标点**。

### 修法一：`initial_prompt`（效果最大，零成本）

给它一段"普通话书面语"示例当上一段转录，它就会对齐成简体 + 带标点。

| 配置 | 耗时 | 繁体字 | 标点 |
|---|---|---|---|
| 不给提示词 | 4.1s | **82** | **0** |
| 给提示词 | **2.4s** | **0** | **11** |

注意加了提示词**反而更快** —— 不用在繁简和断句上纠结，收敛更早。

提示词表按语言分开（中/英/日/韩各一份），由检测出的语言决定用哪条。

### 修法二：OpenCC 兜底

提示词偶尔仍会漏个别繁体字。中文结果再过一遍 `opencc` 的 `t2s`。
没装 opencc 就原样返回（`try/except`），不影响主流程。

### 修法三：换更大的模型

`base` 对中文偏弱。同一段音频对比：

| base 输出 | small 输出 | 正确 |
|---|---|---|
| 焦跌平衡 | 折叠评论 | 折叠/铰链 |
| 零字折跌 | 零字折叠 | 折叠 |
| 这个量平 | **亮屏** | 亮屏 |
| iPhone **2** | iPhone **Duo** | iPhone Duo |
| 土家 | **独家** | 独家 |

所以默认模型是 `small`。纯英文用 `base` 也够（约 21x 实时）。

## 5. 断点续跑

### 踩过的坑：按块存档太粗

第一版是"每 5 分钟一块，块转完才存"。`small` 模型一块要算约 40 秒，
所以**在前 40 秒内中断等于一点进度都没存** —— 表现为"停止后重启还是从头来"。

### 现在的做法：段级存档

每产生几条字幕（**攒够 3 条 或 距上次超过 2 秒**，双阈值）就把已转部分写进
`audio/<名字>.segments.json`。

只用条数阈值不够：`small` 一段 30 秒音频要算 4 秒左右，攒够 10 条要 40 秒，
用户在前 40 秒内中断仍然什么都存不下。

### 三个关键设计

**① 续跑点精确到秒**

```python
resume_at = 已存最后一条字幕的 end
start_sec = max(0, resume_at - RESUME_OVERLAP)   # 往回退 2 秒
```

**② 重叠去重**

往回退 2 秒会重复转一小段，按时间戳丢弃：`if item["start"] < resume_at - 0.05: continue`

**③ 指纹 + 原子写**

```
v4|small|auto+multi|60|17331426|1791458772
└版本└模型└语言────┘└块长└文件大小└修改时间
```

模型/语言/音频变了，旧进度自动作废。写入用 `.tmp` + `os.replace`，
进程被强杀也不会留下半截 JSON。

### 实测

12 分钟音频，跑 25 秒后按停止：

```
✓ 存档 24 条，续跑点 116.0s / 720s

重启：
[续跑] 已有 24 条字幕，从 1:56 处继续（共 12:00）
待转 10:06，分 3 段处理
--- 第 1/3 段：1:54 ~ 6:56     ← 116s 往回退 2s
```

最终 Markdown：时间戳单调递增、无重复段落。

## 6. 阶段耗时面板

进度条下面那排显示五个阶段的状态和秒数。

**两个坑：**

**① 输出被块缓冲**
Python 的 stdout 重定向到管道时默认块缓冲（约 8KB）。阶段 1~3 输出很少，
凑不满缓冲区就一直不吐，界面看起来像卡在"正在启动"。
修法：`PYTHONUNBUFFERED=1` + 命令行 `-u`。

**② 定时刷新链自己把自己杀了**
```python
if self._stage_idx >= 0 and self.running:   # 第一次调用时还是 -1
    self.root.after(100, self._tick_stages)  # 这行永远执行不到
```
改成无条件自续（`if not running: return` 之后直接排下一次）。

## 7. 加速手段

| 手段 | 收益 | 说明 |
|---|---|---|
| faster-whisper + CTranslate2 | 数倍 | int8 量化 + 优化内核 |
| `compute_type="int8"`（CPU） | 约 2~3x | 权重缩到 25%，准确率几乎无损 |
| `beam_size=1` | 3~5x | 贪心解码；默认 5 慢 3~5 倍而准确率提升有限 |
| `vad_filter=True` | 视静音比例 | 掐掉静音段，既快又减少幻听 |
| 只下音轨 | 下载 3~5x | 110 分钟视频 50MB 而非 220MB，且不用合并音视频 |
| ffmpeg `-vn` | 约 1s/视频 | 不解码视频流 |
| 模型实例复用 | **约 47%** | 分块后每块都新建模型会重复加载，缓存后从 289s → 152.8s |
| CUDA DLL 预检 | 省几十秒 | 没有 cuBLAS 时不要白试一次 GPU（失败前要耗几十秒） |

**实测总账**（8:46 英文视频，526 秒音频，CPU int8）：

| 阶段 | 耗时 | 倍率 |
|---|---|---|
| 下载音频（6.8 MB） | 2.9s | — |
| FFmpeg 提取 | 2.4s | 219x |
| 转写（base） | 24.3s | 21.7x |
| 转写（small） | ~70s | 7.9x |

## 8. 已知限制

| 限制 | 影响 | 可能的修法 |
|---|---|---|
| 中文标点可能混用半角 | 中英混合块被判成英文时会用英文标点风格 | 后处理：中文语境里的 `,` `?` `!` 转全角 |
| `vad_filter` 会误删语音 | 实测有把 0~9s、38~57s 正常语音判成静音的情况 | 调 `min_silence_duration_ms`，或关掉 VAD |
| 纯音乐/无语音段 | 仍可能产生短幻觉 | `hallucination_silence_threshold` 已缓解 |
| 句级语言切换 | 一句里中英混着说时，按块检测帮不上 | 需要句级检测（代价大） |
| 无 GPU 加速 | CPU 上 small 约 8x 实时 | 装 CUDA 运行库后自动启用 |

## 10. 说话人分离（可选）

完整的功能说明在 [主 README](../README.md#说话人分离可选)，这里只记实现上的几个决定。

### 为什么放在【转写之前】做

分离只需要音频，不需要转写结果。但顺序决定了三件事：

1. 每条字幕一产生就带上 `speaker`，`persist()` 直接存进检查点 —— **续跑不用重做分离**
2. 检查点指纹里带上 `spk{人数}@{阈值}`，改了参数旧进度自动作废
3. 分离失败时能立刻报错，不用等转写跑完十分钟才发现

代价是没法"先转写、后决定要不要分离"。但分离是命令行开关，天然是事先决定的。

### 为什么自己写 `diarize.py` 而不是塞进 `pipeline.py`

主流水线已经 1500+ 行。分离是**完全独立的能力**：输入是音频数组，输出是时间区间列表，
和五层流水线没有任何耦合。单独一个模块的好处：

- sherpa-onnx 的 import 只在真正调用时发生，不做分离的人完全不加载
- 模型下载逻辑是自包含的，出问题好定位
- 单元测试可以只 import `diarize`，不用把 whisper 也拖进来

### 说话人编号要重排

聚类输出的编号是**稀疏的**：一段素材可能只用到 0 和 3。直接输出就是 `S1` 和 `S4`，
看的人会以为漏了两个人。所以 `write_markdown` 会按实际出现顺序重排成 0,1,2…
输出就是连续的 `S1`、`S2`。

### 字幕归属：按重叠时长而不是起点

换人常常正好落在句子中间，字幕起点还压在上一句的尾音里。按起点判会整句判错。
取重叠最多的那段说话人区间更稳（`diarize.best_speaker`）。

### 已知限制

| 限制 | 说明 |
|---|---|
| 不给出真实姓名 | 只回答"哪段是谁"，S1/S2 是聚类编号，跨视频不保证一致 |
| 阈值敏感 | 0.5~0.7 会把一个人拆成多个；默认 0.9 偏保守，已知人数时用 `--num-speakers` |
| 重叠说话 | 两人同时说话时只能归给一人 |
| 唱歌/音乐段 | 会被当成说话人，可能污染聚类 |
| 耗时翻倍 | 150 秒音频分离要 28 秒，与转写相当 |

## 9. 平台差异

| | Windows | macOS / Linux |
|---|---|---|
| `pipeline.py` / `check_env.py` | ✅ | ✅ 只依赖 FFmpeg + Python |
| `app.py`（GUI） | ✅ 完整 | ⚠️ 能跑，但这些功能不可用：`shlwapi` 文件关联查询、`os.startfile`、`.ps1` 快捷方式、`CREATE_NO_WINDOW` 抑制黑框 |

GUI 里"打开文件/所在文件夹"用了三级降级（`cmd /c start` → `ShellExecuteW` → `subprocess`），
因为某些 Windows 环境下 `explorer.exe` / `Code.exe` 会以 `0xC0000142`（DLL 初始化失败）
或 `0x80000003`（断点）退出。完整诊断见 `tools/诊断打开方式.bat`。
